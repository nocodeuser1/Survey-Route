# Drain-valve Yes/No checklist change

Base: `nocodeuser1/Survey-Route`, `main`, `73a714e4184ee4e59596fd890e9a0094bb9eaef9`.

## Behavior

The existing `drain_valves_presence` checklist item now has Yes and No controls
inside the same site-visit checklist. This covers both facility-detail and SPCC
plan-detail modals. The other eight default items remain ordinary checkboxes.

- An unanswered item starts with neither option selected
- Both Yes and No count as a completed observation
- Either answer can be changed, or cleared to unanswered
- Reset for next visit clears answers and ticks
- Old completion timestamps remain preserved and display as previously checked,
  with no inferred Yes/No answer. They do not satisfy this new question
- Saved templates, custom labels, and reordering retain the control through the
  stable item id. Settings identifies it with a Yes / No badge
- Saves are serialized per facility. Leaving and returning to a pending facility
  restores its optimistic answer and disabled controls until the save completes
- A failed save rolls back and shows an error. Existing offline behavior is
  unchanged: the checklist does not queue offline changes

## Storage and compatibility

No database migration or production data rewrite is needed. The existing JSONB
column remains a map of strings:

```json
{
  "drain_valves_presence": "2026-10-02T15:00:00.000Z",
  "__answer:drain_valves_presence": "{\"answer\":\"no\",\"answeredAt\":\"2026-10-02T15:00:00.000Z\"}"
}
```

The reserved `__answer:` prefix cannot be generated by the Settings item-id
builder and is excluded from normalized template items. Responses are accepted
only when the explicit `yes`/`no` value and valid timestamp match the primary
completion timestamp. A legacy tick alone never implies an answer.

String metadata is intentional: older web/native versions keep only strings
when normalizing progress. They therefore retain this answer when toggling an
unrelated item after loading it. Their drain control still shows completion,
not the answer. Unchecking/rechecking that old control invalidates the answer
because its timestamp no longer matches. An older client's Reset clears it.

As before, updates replace the facility's entire progress object. Concurrent
stale clients can overwrite each other; this change does not implement
cross-device conflict resolution. Refresh/update clients for the Yes/No UI.

IndexedDB caches, snapshots, and JSON backup/restore preserve these strings.
The existing CSV/XLSX reports do not export any site-visit checklist fields, so
there is no affected Yes/No export formatter.

## Verification

Run the dependency-locked checks:

```sh
npm ci
node --test tests/*.test.ts
npx --no-install eslint src/utils/siteVisitChecklist.ts src/components/SiteVisitChecklist.tsx src/components/SiteVisitChecklistSettings.tsx tests/siteVisitChecklist.test.ts tests/siteVisitChecklist.integration.mjs
npm run build
npm run typecheck
npm run lint
```

The integration runner bundles the actual React components with a local mock
Supabase adapter. It uses synthetic facilities only and never connects to the
live backend. Optional test tools are installed outside the repository so the
application dependency lockfile stays unchanged:

```sh
npm install --prefix /tmp/survey-route-test-tools --save-exact playwright@1.63.0 jsdom@30.1.1
QA_DOM=1 \
JSDOM_MODULE=/tmp/survey-route-test-tools/node_modules/jsdom/lib/api.js \
node tests/siteVisitChecklist.integration.mjs
```

For real Chromium layout tests on an environment that permits browser processes:

```sh
PLAYWRIGHT_MODULE=/tmp/survey-route-test-tools/node_modules/playwright/index.mjs \
CHROMIUM_PATH=/usr/bin/chromium \
node tests/siteVisitChecklist.integration.mjs
```

Optional `QA_OUTPUT_DIR` selects a directory for test results/screenshots.
`QA_PREVIEW=1` starts the isolated mock preview without running assertions.
